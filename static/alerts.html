System Documentation

Alert Scheduling Engine

How user alerts are scheduled, evaluated against the Go server across trading days, and delivered — with the code that does it.

STATUS · implemented STACK · AdonisJS 6 + Lucid · PostgreSQL · Go TZ · Asia/Kathmandu (Mon–Fri)

What it does

A user creates an alert: a stock symbol + a condition formula (e.g. RSI(Daily, CLOSE, 0, 14) > 30) + a trigger (when to check) + an expiry (when to stop). The engine repeatedly hands that formula to the Go evaluator on the right schedule, and when the condition is met it notifies the user.

The design splits cleanly into two concerns:

  • alerts table — the source of truth: what the alert is (formula, trigger, expiry). Owned by the user.
  • alert_schedules table — a rebuildable cache: when to next evaluate it. Owned by the engine. Wipe it and it rebuilds identically from alerts + the trading calendar.
Design invariantnext_run_at is always derived from the alert's trigger through one calculator and capped against expired_at. No schedule state exists that can't be recomputed — so a bug is fixable by rebuilding, never a permanent corruption.

End-to-end flow

One evaluation, from cron tick to email:

# 1. OS cron fires every minute
$ node ace alerts:poll

# 2. Service atomically claims every schedule whose next_run_at <= now
#    (FOR UPDATE SKIP LOCKED → concurrency-safe)
   alert_schedules: status pending → running

# 3. Dispatcher builds the payload and calls Go
   runGoMain("alert", { formulas: [{ formula, stocks:[SYMBOL], look_back_candle, info:{id} }] })

# 4. Go evaluates the formula against the symbol's candles, returns matches
   [{ selectedStocks: ["NABIL"], lookBackCandle: 0, values: {...} }]

# 5. Match → notify the owner (email); then advance the schedule
   AlertNotifier.notify()  ·  alert.last_trigger_at = now
   alert_schedules: status running → pending, next_run_at = <next occurrence>
                                    (or → expired if ONCE_* fired / past expiry)

The alert_schedules table

One row per alert (alert_id is UNIQUE, ON DELETE CASCADE — deleting an alert removes its schedule automatically). Migration: 1783800000000_create_alert_schedules_table.ts, model: app/models/alert_schedule.ts.

ColumnTypePurpose
alert_idFK uniqueOwning alert. Cascade-deletes.
next_run_attimestamptzWhen the poller next evaluates. NULL = terminal (nothing more to do).
run_kindintraday | eodWhich checkpoint next_run_at points at. Only the N-minute trigger alternates.
statusenumpending running expired
claimed_attimestamptzSet when a tick claims the row; the reconcile job reaps rows stuck past the stale window.
last_evaluated_trading_datedateLast trading day actually evaluated — drives catch-up sizing.
attempt_countintConsecutive Go failures; feeds retry backoff.

Hot path index (status, next_run_at) keeps the poller's "give me everything due" query fast as alert volume grows. The model exposes a due scope encapsulating that predicate:

// app/models/alert_schedule.ts
static due = scope((query) => {
  query
    .where('status', 'pending')
    .whereNotNull('next_run_at')
    .where('next_run_at', '<=', DateTime.now().toSQL()!)
})

Lifecycle & states

created→ pending— claim → running— evaluated → pending⟳ next occurrence
running— ONCE_* fired / past expiry → expired(next_run_at = NULL, terminal)
running— worker crash → stale— reconcile reaps → pending
running— Go error → pending(next_run_at += backoff)

Transitions are the whole engine. pending → running is the atomic claim. running → pending re-arms via the calculator. running → expired is the only terminal edge. Failures never lose a run — they back off and stay pending.

Trigger → next run

The single calculator computeNextRun() maps every trigger type (defined in constants.ts) to its next fire instant. It knows only cadence — expiry is applied by the caller.

Trigger typeParamsNext runrun_kind
ONCE_LIVE—Now if market open, else next session open. Terminal after a match.intraday
ONCE_EOD—Today's close if before it on a trading day, else next trading day's close. Terminal after a match.eod
RECURRING_TRADING_DAY_EOD—Next trading day's close, every day.eod
RECURRING_DAY_OF_WEEK_EODday_of_weekClose on the next matching weekday.eod
RECURRING_TIME_OF_DAYtime_of_dayHH:mm on the next trading day, after now.intraday
RECURRING_N_MINUTES_LIVE_EODinterval_minutes+interval within the session; at close flip to one EOD recheck; then roll to next day's open.intraday ⇄ eod
Why one N-minute row alternates instead of two rowsThe invariant is one schedule row per alert. Spawning a second row for the EOD checkpoint would break the advance logic. Instead run_kind tracks which checkpoint next_run_at currently points at, and the calculator flips it: after the last intraday tick → eod at close → next day's first intraday tick.

Verified against a fixed reference (Wed 2026-07-15 09:00, before the 11:00 open):

ONCE_EOD                  → 2026-07-15T15:00  [eod]     # today's close
ONCE_EOD (after match)    → TERMINAL (null)             # disables itself
DAY_OF_WEEK friday        → 2026-07-17T15:00  [eod]     # next Friday
TIME_OF_DAY 14:30         → 2026-07-15T14:30  [intraday]
N_MINUTES 30 (pre-open)   → 2026-07-15T11:00  [intraday] # first tick at open
N_MINUTES 30 @12:00       → 2026-07-15T12:30  [intraday] # +30m step
N_MINUTES 30 @14:50       → 2026-07-15T15:00  [eod]      # past last slot → flip

Expiry → expired_at

Expiry lives on the alerts table as a concrete timestamp expired_at, computed once from the expiry rule in alerts_controller.ts (computeExpiredAt). The Alert.active scope filters on it so expired alerts are never scheduled or evaluated.

Expiry typeParamsexpired_at
NEXT_N_TRADING_DAYStrading_daysEnd of the N-th trading day from creation (Sat/Sun skipped).
ON_DATEdateEnd of the given date.
NEVER—NULL — stays active until deleted.
Edit-drift guardNEXT_N_TRADING_DAYS is anchored to "now", so expired_at is recomputed only when the expiry rule actually changes. Editing an unrelated field (name, formula) must not silently push the countdown out. Same principle drives syncForAlert: cadence is recomputed on every edit through the one calculator, so no field can drift.

The service applies the cap in one place — any next run beyond expiry terminates the schedule:

// alert_schedule_service.ts · applyNextRun (shared by sync + advance)
const active = !alert.expiredAt || alert.expiredAt > from
const next = active ? computeNextRun(alert.trigger, from, { ...opts, currentRunKind }) : null

if (next && (!alert.expiredAt || next.nextRunAt <= alert.expiredAt)) {
  schedule.status = 'pending'; schedule.nextRunAt = next.nextRunAt; schedule.runKind = next.runKind
} else {
  schedule.status = 'expired'; schedule.nextRunAt = null   // terminal
}

Trading calendar

trading_calendar.ts is the only file that answers "is this a trading day?". The current rule: Saturday and Sunday are the only non-trading days — there is no separate exchange-holiday table yet. When one is added, only isTradingDay() changes; every other function composes on top of it.

Hours and timezone are constants in market_config.ts, overridable by env:

MARKET_TIMEZONE = 'Asia/Kathmandu'   // all schedule math runs in this zone
MARKET_OPEN     = '11:00'
MARKET_CLOSE    = '15:00'
TRADING_WEEKDAYS = [1,2,3,4,5]      // Luxon Mon=1 … Fri=5

Helpers the rest of the engine builds on: nextTradingDay, marketOpenOn / marketCloseOn, isMarketOpenAt, addTradingDays (expiry), and subtractTradingDays / countTradingDaysInclusive (catch-up).

Catch-up: sizing look_back_candle

If the poller misses runs (downtime, holiday gap), a single-candle check would silently skip days. The dispatcher sizes the look-back window to cover every trading day since last_evaluated_trading_date:

// alert_dispatcher.ts
private lookBackCandles(schedule, evaluatedTradingDate) {
  if (!schedule.lastEvaluatedTradingDate) return 1            // first run
  const gap = countTradingDaysInclusive(schedule.lastEvaluatedTradingDate, evaluatedTradingDate)
  return Math.min(Math.max(gap, 1), MAX_LOOK_BACK)      // capped at 30
}

Go returns one result row per candle (lookBackCandle = candle index, 0 = most recent). The dispatcher takes the lowest-index match as "most recent" and maps that index back to a trading date via subtractTradingDays.

The 4 update points

Every moment a schedule row can change, and who drives it:

#MomentEntryEffect
1Alert createdcontroller.store → syncForAlertInsert row, first next_run_at from trigger.
2Alert editedcontroller.update → syncForAlertRecompute cadence & expiry cap (idempotent upsert).
3Go result returnsrunDueBatch → advanceAdvance to next occurrence, or terminate.
4Daily safety netreconcileDailyReap stale, expire passed, backfill missing.
Point #2 is the one people forgetIf a user changes trigger or expiry, the old next_run_at is stale. syncForAlert is idempotent and re-derives from scratch, so create and edit share one path — the same class of bug the earlier expired_at fix closed.

The poll tick

runDueBatch() is the heart. It claims due rows atomically, so two concurrent ticks (or scaled-out pollers) never double-dispatch the same alert:

-- Atomic claim: pending + due → running, in one statement
UPDATE alert_schedules
   SET status = 'running', claimed_at = ?, updated_at = ?
 WHERE id IN (
   SELECT id FROM alert_schedules
    WHERE status = 'pending' AND next_run_at <= ?
    ORDER BY next_run_at ASC
    LIMIT ? FOR UPDATE SKIP LOCKED   -- the concurrency guarantee
 ) RETURNING id;

Each claimed row is then processed: evaluate → notify on match → advance. A failure backs off and re-arms instead of losing the run:

for (const schedule of claimedSchedules) {
  try {
    const ev = await alertDispatcher.evaluate(alert, schedule, now)
    if (ev.matched) await alertNotifier.notify(alert, { matchedOn: ev.matchedOn, values: ev.values })
    schedule.lastEvaluatedTradingDate = ev.evaluatedTradingDate
    applyNextRun(schedule, alert, now, { afterMatch: ev.matched })   // re-arm or expire
  } catch (err) {
    schedule.attemptCount += 1
    schedule.nextRunAt = now.plus({ minutes: Math.min(schedule.attemptCount, 5) })  // backoff
    schedule.status = 'pending'
  }
  await schedule.save()
}

Go payload & result

The dispatcher is the sole owner of the wire format. It calls runGoMain("alert", …), which shells out to the Go shell_runner. Payload:

{
  "formulas": [{
    "formula": "RSI(Daily, CLOSE, 0, 14) > 30",   // alert.conditionFormula.equation
    "all_stocks": false,                        // single-symbol → specific-stocks path
    "stocks": ["NABIL"],                       // [alert.symbol]
    "look_back_candle": 1,                     // catch-up window (see above)
    "info": { "id": 42, "alertId": 7 }        // id = schedule.id ← correlation token
  }]
}
Why info.id = schedule.id (not alert.id)The schedule row is what asked for the evaluation, so its id is the correlation token the result maps back to. Today the call is synchronous, so correlation is trivial — but if this later moves to a daemon + webhook (Go pushes results back over HTTP), schedule.id is the token the webhook echoes, and a stale/duplicate delivery can be rejected by checking the row is still running.

Go side — a new case in shell_runner/main.go reuses the exact scanner evaluation core, but takes formulas inline instead of fetching by scanner id:

case "alert":
    formulasRaw, ok := input["formulas"]
    if !ok { /* error: formulas required */ }
    results := indicatorprocess.Run(formulasRaw)   // same engine as the scanner path
    bytes, _ := json.Marshal(results)
    helpers.SendToDispatcher(bytes)

Result rows the app reads (subset of DetailedFormulaOutput): selectedStocks[], lookBackCandle, values. A match = any row whose selectedStocks contains the symbol.

Daily reconcile (safety net)

Event-driven advance (point #3) is the primary mechanism — precise and cheap. reconcileDaily() is purely a correctness sweep for drift the poll can't catch:

  • Reap stale — rows stuck running past the stale window (5 min; Go exec times out at 30s) are reset to pending. Recovers crashed/killed workers.
  • Expire passed — schedules whose alert's expired_at has passed → expired, next_run_at = NULL.
  • Backfill missing — any Alert.active with no schedule row gets one via syncForAlert. Self-heals partial failures.

Run after EOD data settles so calendar-anchored triggers land on fresh data.

Deployment

The commands exist; scheduling them is deployment config. OS cron:

# Poll every minute — evaluate all due schedules
* * * * * cd /app && node ace alerts:poll  >> /var/log/alerts_poll.log 2>&1

# Reconcile once daily at 18:00 market time — after EOD settles
0 18 * * * cd /app && node ace alerts:reconcile  >> /var/log/alerts_reconcile.log 2>&1
Perf noterunGoMain currently shells go run per call (fresh toolchain each time). Fine at low volume; for tight N-minute intervals across many alerts, go build a binary once and exec that instead. Independent of this engine.

Extension seams

Email delivery@adonisjs/mail is not installed, so AlertNotifier.sendEmail currently logs "ALERT FIRED". The whole fire → notify pipeline is wired up to the send; only the transport is missing. Replace the log with mail.send(...) (preload the owning User for the address).
Exchange holidaysOnly Sat/Sun are non-trading today. Add a holiday table and consult it inside trading_calendar.isTradingDay() — nothing else changes.
Market hours / timezoneGuessed as 11:00–15:00 Asia/Kathmandu. Confirm against the real exchange and override via MARKET_OPEN / MARKET_CLOSE / MARKET_TIMEZONE env vars.
Async webhook (future)To move off synchronous exec: have Go POST results to an app endpoint, keyed by info.id = schedule.id. The receiver applies the result only if the row is still running (dedupes late/duplicate deliveries), then advances — the same applyNextRun the sync path uses.
